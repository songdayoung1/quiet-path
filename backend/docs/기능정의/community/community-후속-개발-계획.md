# Community 후속 개발 계획

## 1. 문서 목적

이 문서는 Quiet Path 커뮤니티 기능의 다음 개발 범위를 정리한 실행 문서다.
목표는 아래 세 가지다.

* 다른 AI나 개발자가 현재 상태를 빠르게 이해하고 같은 기준으로 이어서 작업할 수 있게 한다.
* MVP 배포 전 꼭 필요한 기능과 나중으로 미룰 기능을 구분한다.
* 캐시, 상태 동기화, 알림, 운영 기능처럼 서로 얽히는 주제를 한 번에 정리한다.

---

## 2. 현재 상태 요약

### 2.1 현재 구현된 범위

* 커뮤니티 feed 조회
* 주간 Top3 조회
* 공감 추가/취소
* 댓글 조회/작성/수정/삭제
* Top3 슬라이드 UI
* Top3와 feed의 기본적인 공감/댓글 수 동기화
* 댓글은 `recordId` 기준으로만 동작
* soft delete 댓글은 DB에는 남고 일반 조회에서는 제외

### 2.2 현재 정책

* 커뮤니티 상호작용의 기준 단위는 `recordId`
* Top3 선정 기준은 최근 7일 공감 수
* Top3 카드에 보여주는 숫자는 총 누적 공감 수
* 같은 `path`의 서로 다른 `record`가 Top3에 함께 들어오는 것은 허용
* Top3는 1~3개만 노출하고, 부족하면 부족한 만큼만 노출
* 하트는 optimistic update 허용
* 댓글은 optimistic update를 하지 않고 재조회로 동기화

### 2.3 현재 데이터 규모

대용량 시드 기준:

* seed users: `150`
* seed paths: `150`
* seed records: `3,600`
* seed reactions: `146,366`
* seed comments: `31,584`

추가로 댓글이 100개 이상 붙는 기록도 일부 생성되어 있다.
즉 현재부터는 댓글 페이지네이션, feed 집계, Top3 집계를 실제 데이터 규모에서 확인할 수 있다.

## 3. 최우선 작업 원칙

### 3.1 MVP 기준 우선순위

1. 커뮤니티 캐시와 상태 동기화
2. 댓글 UX 개선
3. Top3 상호작용 안정화
4. 기록 공유 기능 연결
5. 기록 상세 조회
6. 알림 기능 정리
7. 신고 및 운영 기능

### 3.2 설계 원칙

* 기준 엔티티는 항상 `recordId`
* 프론트 캐시는 이번 단계의 핵심이 아님
* 백엔드 중심으로 `Redis + 쿼리 최적화`를 우선 적용
* 모든 읽기 API를 캐시하지 않고, 효과가 큰 조회만 캐시
* 댓글은 상태 정합성을 우선하고, 하트는 반응성을 우선한다

## 4. 캐시와 상태 동기화 계획

## 4.1 목표

커뮤니티 첫 진입 시 체감 로딩을 줄이고, 하트/댓글 이후 feed와 Top3의 상태 불일치를 막는다.

## 4.2 캐시 적용 대상

### 1순위

* `feed` 첫 페이지

적용 이유:

* 커뮤니티 첫 진입에서 가장 먼저 체감되는 데이터다.
* 공개 기록이 늘수록 count 집계와 정렬 비용이 커질 수 있다.
* 전체 페이지 캐시보다 첫 페이지 캐시가 무효화 범위를 관리하기 쉽다.

### 2순위

* `weeklyTop3`

현재 판단:

* 바로 Redis에 넣지 않아도 된다.
* 먼저 쿼리 최적화와 실제 응답 시간을 본다.
* feed 최적화 후에도 병목이면 Redis 캐시를 추가한다.

### 이번 단계에서 제외

* `comments`

제외 이유:

* 수정/삭제/작성에 따른 무효화가 잦다.
* 페이지 단위 관리 비용이 크다.
* 댓글은 현재 병목 후보 1순위가 아니다.

## 4.3 캐시 계층

### DB

* 정답 저장소
* 인덱스/쿼리 최적화 대상
* 앱 레벨 캐시 대체재로 보지 않는다

### Redis

* 서버 공유 캐시
* `feed first page`를 첫 적용 대상으로 본다
* 필요 시 `weeklyTop3` 확장

### 프론트 메모리 캐시

* 이번 단계 핵심 범위에서 제외
* 후속 개선 항목으로만 둔다

## 4.4 캐시 키 초안

### feed

* `community:feed:first:{category}`
* category는 `all | job | study | workout | hobby | cert`

비고:

* 인증 사용자별로 `isReacted`가 달라지는 구조라면 캐시 payload에는 공통 데이터만 넣고,
  사용자별 공감 여부는 별도 overlay 하거나 캐시 적용 범위를 guest/all 공개 payload 중심으로 제한한다.
* MVP 단계에서는 `feed 공통 payload + 사용자별 reactedRecordIds 조회` 구조가 가장 현실적이다.

### weeklyTop3

* 필요 시 `community:weekly-top3`

초기에는 Redis 미적용 권장

## 4.5 무효화 규칙

### 공감 추가/취소

영향 범위:

* `feed`
* `weeklyTop3`

처리 원칙:

* 프론트는 현재 보이는 카드만 optimistic update
* 서버 성공 후 관련 feed 캐시 무효화
* `weeklyTop3`는 순위 변동 가능성이 있으므로 재조회 또는 캐시 무효화

### 댓글 작성

영향 범위:

* 해당 `recordId`의 댓글 목록
* `feed`
* `weeklyTop3`

처리 원칙:

* 댓글 목록은 서버 기준으로 첫 페이지 재조회
* 댓글 수는 재조회 결과의 `totalElements` 기준으로 갱신
* feed / Top3 count도 같은 `recordId` 기준으로 반영

### 댓글 수정

영향 범위:

* 해당 `recordId`의 댓글 목록

처리 원칙:

* count는 바뀌지 않으므로 feed / Top3 캐시 무효화는 필요 없음
* 댓글 목록만 재조회

### 댓글 삭제

영향 범위:

* 해당 `recordId`의 댓글 목록
* `feed`
* `weeklyTop3`

처리 원칙:

* 댓글 작성과 동일
* count 감소를 서버 응답 기준으로 다시 맞춘다

## 4.6 상태 동기화 규칙

### recordId 단일 소스 원칙

아래가 모두 같은 `recordId`를 기준으로 움직여야 한다.

* feed 카드의 `reactionCount`
* feed 카드의 `commentCount`
* Top3 카드의 `reactionCount`
* Top3 카드의 `commentCount`
* `isReacted`

즉 같은 기록이 여러 위치에 보여도 상태 기준은 하나다.

### 카테고리 전환 시 초기화

초기화 대상:

* 열린 댓글 시트
* 선택된 댓글 대상 record
* feed pagination cursor
* category-specific loading state

유지 대상:

* 로그인 상태
* 이미 불러온 현재 화면 외 전역 상태

## 5. 댓글 UX 개선 계획

## 5.1 목표

댓글이 많아져도 읽기와 작성이 자연스럽고, 카드와 댓글 시트가 엉키지 않게 만든다.

## 5.2 작업 범위

### 댓글 더보기 / 추가 로드

* 첫 페이지 10개 또는 20개 기준 확정
* `더보기` 또는 스크롤 추가 로드 중 하나로 통일
* 100개 이상 댓글 기록에서도 마지막 페이지까지 안정적으로 조회

### 작성 / 수정 / 삭제 흐름 정리

* 작성 중 중복 제출 방지
* 수정 중 대상 변경 시 상태 초기화
* 삭제 확인 모달/시트 정리
* 실패 시 에러 메시지와 재시도 경로 단순화

### 카드와 댓글 시트 전환 안정화

* A 카드 댓글 열림 상태에서 B 카드로 이동 시 상태 꼬임 방지
* Top3 슬라이드 이동 중 열린 댓글 시트 정리
* feed 카드와 Top3 카드가 같은 record를 공유할 때 상태 충돌 방지

### 모바일 입력/스크롤 개선

* 키보드 열릴 때 입력창 가려짐 방지
* 시트 내부 스크롤과 배경 스크롤 충돌 방지
* 긴 댓글 입력 시 textarea 자동 높이 조절 안정화

## 5.3 완료 기준

* 댓글 100개 이상 기록에서도 첫 페이지 진입과 추가 로드가 정상 동작
* 작성/수정/삭제 후 count가 feed / Top3와 불일치하지 않음
* 모바일에서 입력창이 가려지거나 스크롤이 튀지 않음

## 6. Top3 상호작용 안정화 계획

## 6.1 목표

Top3가 독립 카드처럼 보이더라도 실제 상태는 feed와 같은 기록을 공유하도록 만든다.

## 6.2 작업 범위

### 하트 후 Top3와 feed 동기화

* 같은 `recordId`면 어느 쪽에서 눌러도 둘 다 반영
* 실패 시 둘 다 롤백

### 댓글 수 변경 시 Top3 반영

* 댓글 작성/삭제 후 Top3 카드 count 갱신
* Top3가 화면에 떠 있지 않아도 다시 열면 최신 값 유지

### 슬라이드 전환과 댓글 열림 상태 정리

* 현재 슬라이드에서 댓글 열림 상태 유지 규칙 확정
* 다른 슬라이드 이동 시 닫을지 유지할지 일관성 있게 처리

### Top3 노출 정책 최종 반영

* 최근 7일 공감 수 기준 선정
* 표시 숫자는 총 공감 수
* 1~3개만 노출
* 같은 path의 다른 record 중복 허용

## 6.3 완료 기준

* 하트/댓글 수가 feed와 Top3 사이에서 어긋나지 않음
* 슬라이드 이동 중 댓글 UI가 깨지지 않음

## 7. 기록 공유 기능 연결 계획

## 7.1 목표

공개 기록을 외부로 공유할 수 있게 하되, MVP에서는 과한 복잡도를 만들지 않는다.

## 7.2 작업 범위

### 카카오톡 공유

* 공유 payload 정의
* 공유 실패/미지원 환경 처리

### 링크 복사

* 기록 상세 진입 URL 또는 공유 URL 설계
* 복사 완료 토스트 처리

### 공유 상태 안내

* 공유 가능/불가 조건 명확화
* 이미 PRIVATE인 기록, 이미 숨긴 기록 등에 대한 안내

## 7.3 선행 조건

* 기록 상세 진입 URL 정책 필요
* 공개 기록 공유용 route 또는 shareCode 사용 방식 정리 필요

## 8. 기록 상세 조회 기능 계획

## 8.1 목표

feed와 Top3 카드에서 잘린 내용을 자연스럽게 더 볼 수 있게 만든다.

## 8.2 작업 범위

### 긴 본문 전체 보기

* 말줄임 카드 + 전체 보기 진입
* 댓글 시트와 별개로 기록 본문 집중 소비 가능하게 구성

### 이미지 포함 기록 확장 보기

* imageUrl이 있는 경우 확장 뷰 제공
* 이미지와 텍스트를 함께 보여준다

### 자연스러운 상세 진입

* feed 카드
* Top3 카드
* 공유 링크

위 세 지점에서 동일한 상세 화면 또는 확장 시트로 연결

## 8.3 완료 기준

* 긴 기록을 카드에서 잘라 보여주되 전체 보기 진입이 가능
* Top3에서 보던 기록과 상세 화면이 같은 recordId로 연결됨

## 9. 알림 기능 통합 계획

## 9.1 왜 통합해서 보아야 하는가

현재 알림은 두 축이 있다.

### 1. 커뮤니티 이벤트 알림

* 댓글 알림
* 공감 알림
* 인앱 알림 목록 기준

### 2. 설정 기반 알림

* 방향 종료 알림
* 좋아요 알림 토글
* 댓글 알림 토글
* 브라우저 권한 및 웹 알림 시간 설정

이 둘을 별도 기능처럼 다루면 사용자 입장에서 같은 “알림 설정”인데 데이터 기준이 분리된다.
따라서 기능 정의는 하나로 묶고, 채널만 나누는 것이 맞다.

## 9.2 통합 기능 정의

알림 기능은 아래 3층으로 나눈다.

### 알림 이벤트

무슨 일이 발생했는가

* `COMMENT_CREATED`
* `REACTION_CREATED`
* `PATH_REVIEW_REMINDER`

### 알림 채널

어디로 보여줄 것인가

* 인앱 알림함
* 웹 브라우저 알림

### 알림 설정

사용자가 무엇을 허용했는가

* 댓글 알림 on/off
* 공감 알림 on/off
* 방향 종료 알림 on/off
* 방향 종료 알림 시간
* 브라우저 권한 상태

## 9.3 이번 단계 목표

### 커뮤니티 알림

* 댓글 알림
* 공감 알림

### 설정 연동

* Settings의 likes/comments/pathEnd 토글을 서버 정책과 맞춘다
* 웹 권한 여부와 서버 저장 상태를 분리해 관리한다

예:

* 서버 설정은 `likes=true`
* 브라우저 권한은 `denied`

이 경우 “원함”은 true지만 “실제 웹 푸시 가능”은 false다.

## 9.4 권장 구현 순서

1. 인앱 알림 도메인 유지
2. 사용자 알림 설정 저장 구조 추가
3. Settings 화면 로컬 상태를 서버 상태와 동기화
4. 웹 알림은 브라우저 권한과 로컬/서버 설정을 함께 보여주도록 정리

## 9.5 완료 기준

* 댓글/공감 알림 생성 여부가 사용자 설정을 따름
* 설정 화면에서 좋아요/댓글/방향 종료 알림을 한 곳에서 관리
* 인앱 알림과 웹 알림 권한 상태가 혼동되지 않음

## 10. 신고 및 운영 기능 계획

## 10.1 목표

관리자 페이지가 없더라도 최소한의 수동 운영이 가능한 구조를 만든다.

## 10.2 작업 범위

### 신고

* 기록 신고
* 댓글 신고

### 숨김 / 차단

* 특정 사용자 숨김
* 특정 기록 비노출

### 운영 처리

* 신고 누적 확인
* 수동 비노출 처리
* soft delete 또는 visibility 조정

## 10.3 MVP 기준

이번 단계에서는 운영 UI보다 아래를 먼저 본다.

* DB 구조
* 최소 API
* 수동 처리 플로우

즉 관리 페이지 없이도 SQL 또는 간단한 운영 API로 처리 가능한 수준까지 정의한다.

## 11. 권장 구현 순서

### Phase 1

* feed 병목 확인
* feed 쿼리 최적화
* feed first page Redis 캐시 적용
* 하트/댓글 무효화 규칙 반영

## 12. 작업 시 체크리스트

### 캐시 / 상태 동기화

* `recordId` 기준 상태를 유지하는가
* 공감 후 feed / Top3가 동시에 맞는가
* 댓글 후 count가 동시에 맞는가
* 카테고리 전환 시 열린 댓글 시트가 정리되는가

### 댓글 UX

* 100개 이상 댓글 record에서 더보기 동작 확인
* 수정/삭제 중 record 전환 시 상태 초기화 확인

### Top3

* 슬라이드 이동과 댓글 시트 상태가 충돌하지 않는가
* Top3 수가 1개일 때도 자연스러운가

### 공유 / 상세

* 공유 URL이 recordId 또는 shareCode 기준으로 안정적인가
* 긴 본문을 카드 밖에서 제대로 읽을 수 있는가

### 알림

* 인앱 알림과 설정 알림 정의가 서로 충돌하지 않는가
* 브라우저 권한이 꺼져 있어도 설정 상태는 유지되는가

## 13. 주의사항

* 예전 사용자 일부 데이터는 `?`로 실제 저장된 이력이 있었음
* 현재는 MySQL 기본 문자셋을 `utf8mb4`로 맞췄으나, 기존 깨진 값은 복구 대상이 아님
* 대용량 시드 기준으로 성능을 보되, MVP에서는 “과한 일반화”보다 “실제 병목 구간 해결”을 우선한다
* 블로그/포트폴리오 관점에서 중요한 축은 `설계`, `캐시`, `배포`, `AI 활용`이다
