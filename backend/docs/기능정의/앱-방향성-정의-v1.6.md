# Quiet Path v1.6 앱 방향성 문서

Quiet Path는 범용 일기 앱이 아니라 `방향을 정하고, 하루를 남기고, 나중에 다시 돌아보게 만드는 회고 앱`이다.  
핵심 경험은 `방향 설정 → 하루 기록 → 방향 마무리 → AI 회고 확인` 흐름에 있으며, 모든 기능은 이 회고 루프를 강화하는 방향으로 설계한다.

v1.6에서는 `종료`와 `새 시작`을 분리하고, `쉬는 상태`를 정상 상태로 받아들이며, `원본 기록`과 `AI 해석물`의 역할을 명확히 나눈다.  
커뮤니티는 유지하지만 핵심 경험이 아닌 보조 경험으로 둔다.

Quiet Path의 제품 정의는 아래와 같다.

- 목표 달성 앱이 아니라, 내가 어떤 방향으로 살고 있었는지 다시 보게 만드는 앱
- 텍스트만 쌓이는 기록 앱이 아니라, 장면과 감정이 남아 회고로 이어지는 앱
- 제약을 통해 철학을 지키되, 사용자가 숨 쉴 여백은 남기는 앱

Quiet Path의 중심 흐름은 아래와 같다.

1. 방향 설정
2. 오늘의 기록 작성
3. 방향 유지
4. 방향 마무리
5. review_at 이후 AI 회고 확인
6. 원할 때 새 방향 시작

핵심 도메인은 아래와 같다.

- Path
- Record
- Path Summary
- Notification

Quiet Path의 제품 원칙은 아래와 같다.

- Quiet Path는 생산성 앱이 아니라 회고 앱이다.
- 기록은 자유 메모보다 `회고 가능한 단위`여야 한다.
- 기능을 더하는 것보다, 철학을 지키는 제약을 먼저 설계한다.
- 홈의 중심은 언제나 `내 방향`, `오늘 기록`, `지난 방향`, `AI 회고`여야 한다.

Path는 사용자가 일정 기간 동안 집중하는 방향이다.  
Path는 질문형 목표보다 `지금 내가 어떤 방향으로 걷고 있는가`를 담는 개념으로 다룬다.

핵심 필드는 아래와 같다.

- `id`
- `user_id`
- `category_code`
- `direction_name`
- `direction_text`
- `review_at`
- `status`
- `cover_record_id`
- `completed_at`
- `created_at`
- `updated_at`

Path 정책은 아래와 같다.

- 사용자는 동시에 `ACTIVE` 방향을 최대 1개까지 가질 수 있다.
- 사용자는 `ACTIVE` 방향이 0개인 상태일 수도 있다.
- `ACTIVE 0개`는 오류 상태가 아니라 `잠시 쉬는 상태`다.
- 방향을 끝내기 위해 새 방향을 바로 만들 필요는 없다.
- `현재 방향 마무리하기`와 `새 방향 시작하기`는 별도 액션이다.
- `COMPLETED`가 되어야 `지나온 방향`으로 이동한다.

이 불변식은 서비스 체크와 DB 제약으로 함께 보장한다.

- 서비스 레이어는 빠른 사용자 피드백을 제공한다.
- DB는 동시 요청에서도 `ACTIVE` 방향 중복 생성을 막는 최후의 보루다.
- 현재 방향의 단일 진실 원천은 `paths.status = ACTIVE`다.
- `users.current_path_id` 같은 중복 상태값은 두지 않는다.

Record는 단순 일기가 아니라 `회고 가능한 하루의 흔적`이다.  
하루를 구성하는 최소 단위이며, 통계, 회고, AI 요약의 입력 데이터가 된다.

핵심 필드는 아래와 같다.

- `id`
- `user_id`
- `path_id`
- `category_code`
- `record_date`
- `scene_text`
- `one_word_text`
- `tomorrow_text`
- `mood_code`
- `image_url`
- `is_hidden`
- `pinned_at`
- `visibility`
- `shared_at`
- `share_code`
- `created_at`
- `updated_at`

Record 정책은 아래와 같다.

- `UNIQUE(user_id, record_date)`를 둔다.
- 하루에 Record는 1개만 존재한다.
- 기록은 `ACTIVE` 방향이 있을 때만 작성할 수 있다.
- 방향이 없는 상태에서는 기록 작성 대신 `새 방향 시작`으로 유도한다.
- 원본 Record는 항상 조회 가능하다.
- Record를 잠그는 UX는 두지 않는다.

Record 의미 구조는 아래와 같다.

- `scene_text`: 오늘 어떤 장면이 있었는지
- `one_word_text`: 오늘 하루를 한 단어로 요약
- `mood_code`: 감정 코드
- `image_url`: 그날의 장면을 기억하게 하는 사진
- `tomorrow_text`: 내일의 작은 행동

이미지 정책은 아래와 같다.

- Record당 이미지 최대 1장
- 사진은 기록의 중심이 아니라 `장면 앵커`다
- SNS형 사진 피드 구조로 확장하지 않는다
- 홈 대표 사진은 Record 핀과 분리해 `Path 대표 장면`으로 다룬다

대표 장면 정책은 아래와 같다.

- `records.pinned_at`은 기록 차원의 `기억할 장면`이다.
- 여러 기록이 `기억할 장면`일 수 있다.
- 홈 대표 사진은 `paths.cover_record_id`로 별도 관리한다.
- `cover_record_id`는 같은 Path 소속이며 이미지가 있는 Record만 가리켜야 한다.

공개 정책은 아래와 같다.

- 기본값은 `PRIVATE`
- 사용자가 명시적으로 공유할 때만 `PUBLIC`
- 공감과 댓글은 공개된 Record에만 허용한다
- 커뮤니티는 `내가 공유한 Record`가 올라가는 구조로 유지한다

AI 회고는 원본 기록과 다른 성격의 결과물이다.  
원본을 숨기는 기능이 아니라, 나중에 도착하는 `해석물`로 다룬다.

Path Summary 정책은 아래와 같다.

- 원본 Record는 언제나 열람 가능하다.
- 잠금 대상은 `AI 회고 결과물`만이다.
- `review_at`은 AI 회고가 열람 가능해지는 시점이다.
- `review_at`이 지나기 전에는 summary row가 존재하더라도 `LOCKED`로 본다.
- `review_at`이 지난 뒤에는 최신 `DONE` 버전을 보여준다.
- 요약이 아직 없으면 `UNLOCKED` 상태에서 생성 대기 또는 준비 중으로 표현한다.

AI 회고 경험 원칙은 아래와 같다.

- 사용자가 쓴 기록은 숨기지 않는다.
- 앱이 나중에 정리해 주는 회고만 늦게 보여준다.
- 타임캡슐 감성은 `차단`보다 `기대감`으로 만든다.
- AI는 기록을 대신 쓰기보다, 지나온 방향을 정리해 주는 역할에 집중한다.

Path Summary 저장 정책은 아래와 같다.

- `path_summaries.version_no`로 버전을 관리한다.
- `(path_id, version_no)`는 유일해야 한다.
- 같은 Path에 대해 여러 번 다시 요약할 수 있다.
- 최신 버전을 기본 표시 대상으로 삼는다.
- `prompt_version`은 프롬프트 템플릿 추적용으로 유지한다.

상태 모델은 아래와 같다.

- Path 상태: `ACTIVE`, `COMPLETED`
- Summary 상태: `PENDING`, `PROCESSING`, `DONE`, `FAILED`, `LOCKED`, `UNLOCKED`

상태 해석 원칙은 아래와 같다.

- `PENDING`은 Path 상태가 아니라 Summary 생성 상태다.
- `쉬는 상태`는 별도 status가 아니라 `ACTIVE Path 부재`로 표현한다.
- `review_at`은 종료 시점이 아니라 회고 개봉 가능 시점이다.
- `completed_at`은 사용자가 실제로 방향을 마무리한 시점이다.

홈 화면과 주요 화면 원칙은 아래와 같다.

- Home은 `현재 방향`, `오늘 기록`, `이번 달 흔적`, `지난 방향` 중심으로 유지한다.
- `ACTIVE 0개`일 때도 홈은 정상 상태로 보여야 한다.
- Direction 화면은 `현재 방향 확인`과 `마무리`에 집중한다.
- Direction 화면에서 방향이 없으면 `새 방향 시작하기`를 주요 CTA로 둔다.
- Past Directions에서는 원본 기록과 AI 회고를 분리해 보여준다.
- 잠금 UI는 AI 회고 영역에만 적용한다.

커뮤니티 방향은 아래와 같다.

- 커뮤니티는 조용히 둘러보는 공간으로 유지한다.
- 과한 실시간성, 과도한 SNS형 보상 구조는 지양한다.
- 커뮤니티 확장보다 공개 정책과 정합성 유지가 우선이다.

기술 설계 원칙은 아래와 같다.

- 정책은 서비스 로직과 DB 제약으로 함께 지킨다.
- 날짜와 시점은 서버가 결정하는 규칙을 우선한다.
- 인프라 과시보다 도메인 불변식과 상태 전이를 명확히 하는 데 집중한다.
- 화면 편의보다 제품 철학과 정합성이 무너지지 않도록 설계한다.

v1.6의 핵심 메시지는 아래 한 줄로 정리한다.

`하루 한 기록, 하나의 방향, 그리고 쉬어갈 자유를 가진 회고 앱`
